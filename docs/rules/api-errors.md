# Ошибки API

Правило действует для ответов API об ошибках в `packages/api/` и их обработки в `packages/client/`.

## Контракт

Ответ с ошибкой имеет тело `{ status, message, violations }`:

- `status` совпадает с HTTP-статусом ответа.
- `message` — непустая строка с общим текстом ошибки.
- `violations` — словарь `Record<string, string>`: ключ — имя поля, значение — сообщение об ошибке.
  Если проверок одного поля несколько, сохраняется первое нарушение в порядке валидации.
- Ошибка без поля (401, 403, 404, 409, 500 и другие) приходит с `violations: {}`, её текст — только в `message`.
- Бэкенд создаёт ошибки полей сразу в формате словаря; старые массивы не поддерживаются.

```json
{
  "status": 422,
  "message": "Username already exists",
  "violations": { "username": "Username already exists" }
}
```

## Клиент

- Клиент разбирает ошибки только через `parseRequestError` из `packages/client/utils/request-error.ts`.
  Нестроковые значения `violations` он отбрасывает; отсутствующий словарь, массив и другой
  некорректный формат заменяет на `{}`. Тело ответа 5xx не читается, используется безопасное
  запасное сообщение и пустой словарь нарушений.
- Формы напрямую присваивают `violations` ошибкам полей и всегда показывают `message`,
  даже если оно совпадает с ошибкой поля. Неизвестные поля в общее сообщение не переносятся.
